# Code audit, 10 October 2026

Where the app stands after eleven rounds, what is left, and what would and
wouldn't be worth changing. Numbers are from the tree as of this date.

## Size and shape

- App: ~24,600 lines of TypeScript/TSX (Astro static site, React islands,
  nanostores, Leaflet, Turf, ArcGIS geodesic ops, protomaps). Server: ~2,400
  lines (Hono, SQLite, SSE). Tests: ~6,300 lines — 267 unit tests (Vitest,
  7 s) and 17 end-to-end tests run on desktop and phone (Playwright, ~1 min).
- 52 runtime dependencies. Built app: 3.9 MB of JavaScript (1.2 MB of it the
  ArcGIS projection engine); the service worker precaches the 56 app files
  only, never the 116 MB of map data, so installing the app is cheap and
  data comes on demand.
- Largest files: CardsPanel.tsx 915, GameSetupDialog.tsx 832, sidebar-l.tsx
  804 (shadcn), gameOps.ts 684, measuring.ts 650, OptionDrawers.tsx 648.
- `any` appears 162 times (PolygonDraw, the card components, overpass,
  references). No TODOs.

## What is left

For playing, nothing blocks: the rules, the shared game, the hider flow,
the deck, the clock and the alerts are in. What remains is polish and
hardening, roughly:

1. A shakedown game and the fixes it brings — every real game so far found
   two or three things (one session).
2. Open questions: Q34 answer countdown, Q35 "asked before" hint, Q37
   scoreboard, Q38 rest periods, Q39 restore the pre-game backup (half a
   session each).
3. Hardening and refactors below (two to four sessions, no new behaviour).
4. Push notifications for a locked phone (free: VAPID keys on the server,
   the service worker shows them; one session) and Authelia in front of
   the site when you want it.

## Architecture

**Sound:** one language and one set of types end to end
(`src/lib/game/types.ts` is read by the server and the phones); the rules
are pure functions with tests (`gameOps.ts`, `deck.ts`, `clock.ts`,
`events.ts`); a static site plus a tiny API; SQLite as a single file;
reference data precomputed on your server; no third-party services; the
e2e suite runs the real server.

**Strained, in order of pain:**

1. **Questions are mutated in place** and the UI is poked with
   `questionModified()` / `triggerLocalRefresh` (61 call sites). React and
   the stores can't see those changes, which is where stale-card bugs come
   from and why sync needs a `synced` map of JSON strings. Fix: an
   `updateQuestion(key, patch)` that writes a new object; mechanical, the
   tests protect it. **Done in Round 12** (same day): no question is
   changed in place any more, and `questionModified` is gone.
2. **Geometry on the main thread.** Every change re-applies every question
   (union/difference of big polygons, sequentially) and then recomputes the
   hiding zones. With twenty questions and 300 stations that's seconds of
   jank on a phone. Fix: a Web Worker for `applyQuestionsToMapGeoData` and
   the zones, plus memoising each question's result by its data, so only
   what changed is recomputed. This is the one change players would feel.
   **Half done in Round 12:** each question's result is remembered by the
   chain before it, the map skips changes it can't see, the zones only
   recompute when the area changed. The worker is still open; try a real
   game first.
3. **God modules.** `context.ts` holds stores and logic (the hider pin
   rules), `session.ts` the connection, sync, known games and hider sync;
   the three big components mix several features. Split by feature (deck
   and hand, setup steps, settings tabs, hider spot).
4. **Full-state broadcast.** Every change sends the whole game to every
   phone over SSE, archive (`rounds`, `moves`, deck log) included; late in
   a long game that is hundreds of kB per tap. Fix: leave `rounds` out of
   the live view (fetch on demand), later send deltas keyed by version.
5. **The hider's role is derived in several places**
   (`hiderMode !== false && (!game || role === "hider")` in the sidebar, the
   Cards tab, the sidebar button, the zone layer). One `computed` store.
   **Done in Round 12:** `hiderPhone`.

  only, the live stream read over fetch (not a cookie: tabs share those).
- ~~Anyone with a game link can delete the game and upload photos~~ **Done
  (round 14):** 100 photos per game; a game with a hider is the hider's to
  delete until a day without changes.
- ~~Displayed clock times mix the server's timestamps with the phone's
  clock~~ **Done (round 14):** every answer carries the server's clock.
- ~~Reconnects retry every 5 s without backoff~~ **Done (round 14):** 5 s
  to 60 s, with "last update … next try in …".
- ~~Randomize Question and Overflowing Chalice are recorded, not
  automated.~~ **Done (round 14).**
- No offline map: tiles and data load on demand; a dead spot means a grey
  map. Caching the play area's tiles would be a feature of its own.
- The phone layout is tested less than desktop: since round 14 the sheet
  tests run on phones too; the shared-game tests still use desktop
  viewports.

## Performance

- Bundle: ArcGIS (1.2 MB + wasm) is there for geodesic buffers; Turf's
  planar buffers would be off by metres at this scale — probably fine for
  a game, and it would halve the download. The `context` chunk (496 kB)
  pulls Turf and the schema into the first load; the `thermometer` chunk
  (472 kB) carries the references/voronoi code and could be lazy.
- Runtime: see architecture point 2. Also each draft's own colour costs one
  extra union/difference per draft; fine for a handful of drafts.
- Server: negligible load; a full JSON write per change is fine for a few
  games.

## Would a rewrite in another stack help?

No. The pain points are inside the structure (in-place mutation, main-thread
geometry, full-state broadcast) and are fixable in place; a different
language or framework would not change them. The libraries the app lives on
— Leaflet, Turf, protomaps, osmtogeojson, d3-geo, the ArcGIS engine — are
JavaScript; a Rust, Go or Kotlin rewrite would bridge or reimplement them.
Sharing one set of types between server and phones is a real asset. A
rewrite would cost weeks and lose eleven rounds of play-tested behaviour
covered by 260 tests. The one framework-level nit is Astro's server
rendering of islands (it bit us once, with `document` in a dialog); plain
Vite + React would remove it, for little else — not worth it now.

2. Geometry worker, if a real game still stutters (the per-question memo
   is in).
3. Split the big files (immutable question updates are in).
4. Live view without the archive; photo cap; token out of the URL; clock
   offset.
5. ~~Q34, Q37, Q39; push notifications~~ (done, round 14); Authelia.
